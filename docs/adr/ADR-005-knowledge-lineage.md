# ADR-005: Knowledge Lineage

**Status:** Accepted
**Date:** 2026-07-27

## Context
For a knowledge foundation to be trustworthy and auditable, every record must
be traceable from its origin through every transformation to its future model.
Without lineage, a factual error or license violation cannot be traced or fixed,
and provenance/attribution obligations (ADR-002) cannot be met.

## Decision
Every Knowledge Object carries a `lineage` object with the full chain:
`source → transformations → knowledge_object → curated_dataset → training_view →
future_model`.
- `source`: origin name (e.g. `OpenAssistant/oasst1`).
- `transformations`: ordered list of pipeline + migration tags applied
  (`clean`, `dedup`, `convert`, `quality_score`, `migrate:001_initial_schema`, ...).
- `knowledge_object`: this object's id.
- `curated_dataset`: target set (e.g. `curated/v0.1`).
- `training_view`: eligible view ids (e.g. `qwen,llama,deepseek`).
- `future_model`: intended downstream class (e.g. `8B-class LLM`).

`source_attribution` (with `source_id` FK to `metadata/source_registry.json`,
`attribution_text`, `share_alike`) provides the license/provenance half of
lineage.

## Alternatives
- Track lineage in an external database. Rejected: breaks portability; the record
  should self-describe.
- Store only the immediate source. Rejected: insufficient for audit/recall.

## Consequences
- Any record can be recalled or regenerated by re-running its recorded
  transformations on its source.
- Lineage is extended (not rewritten) by migrations, so historical raw data
  stays immutable (ADR-005 / ADR-006).
- 100% lineage tracking is a pilot success criterion and is validated structurally
  by `validate_knowledge_object.py`.
