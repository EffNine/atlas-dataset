## 1. Objective

## 2. Test Fixture

A synthetic dataset of exactly **100 raw lines** was generated by `tests/generate_synthetic_test.py` (deterministic, `seed=42`) into `raw/generated/synthetic_test_v1.jsonl`, engineered to exercise every pipeline branch:

| Bucket | Count | Intent |
|---|---|---|
| Unique valid records | 56 | Full metadata, across the 5 requested categories, with mixed quality tiers (high / medium-truncated / low-terse answers) |
| Exact duplicates | 10 | Content-identical copies of unique records, distinct `id` |
| Near duplicates | 5 | One unique record + a short appended clause (Jaccard ≥ 0.8, below exact hash) |
| Missing-metadata | 23 | Valid content but `source`/`tags`/`notes` omitted (to test cleaner backfill) |
| Invalid objects | 5 | empty messages; user-only; unknown category; missing category; message item missing `content` |
| Malformed JSON line | 1 | non-JSON text line |

**Category coverage** (canonical IDs; friendly names in the task map to these):

| Task name | Canonical `category` |
|---|---|
| `software_engineering` | `02_software_engineering` |
| `system_engineering` | `03_system_engineering` |
| `ai_ml` | `04_ai_machine_learning` |
| `hardware_engineering` | `05_hardware_engineering` |
| `general_reasoning` | `01_foundation` |

> **Note on category names:** the task used short friendly names (`software_engineering`, `ai_ml`, …). The canonical schema uses *prefixed* IDs (`02_software_engineering`, `04_ai_machine_learning`). The generator emits canonical IDs so the bulk of the pipeline is validated end-to-end. The cleaner's handling of the raw friendly names was probed separately (see Issue #4). A `tests/synthetic_test_manifest.json` records expected outcomes so the verifier can assert them exactly.

## 5. Issues Found & Fixes Applied

### 🔴 Issue #1 — Validator crashes offline when `jsonschema` is installed
- **Severity:** High (blocks `validate` in any environment with `jsonschema`, including this one).
- **Root cause:** `validate_dataset.py` built `Draft202012Validator(schema)` with no resolver. The canonical `dataset_schema.json` uses `$ref: "chat_schema.json#/$defs/message"` with `$id: https://atlas.dataset/schemas/...`. The referencing engine resolved that `$ref` against the `$id` and tried to **fetch it over the network**. Offline → `referencing.exceptions.Unretrievable` crash.
- **Contradicts:** README claim that the pipeline is "stdlib-only and runs anywhere."
- **Fix:** `strict_jsonschema()` now pre-loads both local schema files into a `referencing.Registry` (offline) and passes it to the validator. Any import/read/registry failure degrades gracefully to the structural validator (which always runs). Confirmed: strict validation now works with **no network**.
- **File:** `scripts/validate_dataset.py`

### 🔴 Issue #2 — Schema rejects `difficulty: 0` (the documented "unassessed" value)
- **Severity:** High (would fail *every* unrated real record).
- **Root cause:** `difficulty` had `minimum: 1` but `default: 0`, and `docs/dataset_design.md` + the schema description both say `0 = unassessed`. The cleaner emits `0` for unrated records, so strict validation rejected 100% of real data.
- **Fix:** set `minimum: 0` and updated the description to `0=unassessed`.
- **File:** `schemas/dataset_schema.json`

### 🔴 Issue #3 — Schema rejects empty `source.date` (the documented "optional" case)
- **Severity:** High (the cleaner emits `date: ""` for records without a known capture date).
- **Root cause:** `date` pattern was `^\d{4}-\d{2}-\d{2}$` (mandatory), but `default: ""` and the design docs say date is optional and "must be resolved before curated/". So every cleaned record without a date failed strict validation.
- **Fix:** pattern now `^(\d{4}-\d{2}-\d{2})?$` (empty allowed), description updated.
- **File:** `schemas/dataset_schema.json`

### 🟡 Issue #4 — Cleaner does not map raw friendly category names
- **Severity:** Medium (usability / future ingestion friction, not a crash).
- **Observed:** `clean_dataset.py` accepts only the **prefixed** canonical IDs (`02_software_engineering`). Feeding it the task's raw names (`software_engineering`, `ai_ml`, `general_reasoning`, …) would be rejected as `unknown category`. The code *attempts* an alias match but the logic is broken — it compares `category` to itself and to `category.split("_",1)[1]`, so it never matches the unprefixed names.
- **Status:** **Documented, not auto-fixed** (deliberate). The canonical taxonomy intentionally uses prefixed, ordered IDs; bulk ingestion should use canonical IDs or an explicit alias map. A clean fix would be a `FRIENDLY_ALIASES` lookup in `clean_dataset.py`. Left as a tracked item rather than silently changing ingestion semantics.
- **File:** `scripts/clean_dataset.py` (alias branch lines ~131–139), `metadata/categories.json`

### 🟢 Issue #5 — Verifier initially used brittle id matching
- **Severity:** Low (test-harness bug, not pipeline).
- **Symptom:** first verification run reported 2 "failures" because (a) dedup *kept the near-dup variant and dropped the original* (it keeps the longest/`highest-quality` member, which was the variant with the appended clause), and (b) clean **auto-assigns ids** to records lacking one, so manifest ids for missing-metadata records didn't match.
- **Fix:** verifier now checks observable *behavior* (near-dup content collapsed to ≤1 copy; missing-metadata content present via stable marker; metadata backfilled) instead of matching auto-generated ids. This correctly reflects that the **pipeline behaved correctly** and the test assumptions were wrong.
- **Files:** `tests/generate_synthetic_test.py` (added `[NEAR-DUP-MARKER]`/`[META-MISSING-MARKER]`), `tests/verify_pipeline.py`
