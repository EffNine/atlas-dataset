## 3. Quality Engine Analysis

### 3.1 Observed Batch 001 evidence

Automatic outputs reported in `review/v0.2/batch_001_input.md` are:

- All reviewed records: `quality_score = 7`
- Confidence range: `0.850` to `1.000`

Human outcomes: 18 approved, 2 needs-revision, 5 rejected.

### 3.2 False positives / false negatives

Because every auto-approved record was given at least score 7, we cannot identify true threshold-style false positives or negatives from this batch alone.
However, useful signal still exists:

- **Approved records with lower confidence:** several approvals came at `confidence = 0.850`–`0.942`. That suggests the engine already treats confidence as a separate risk signal, but it did not route those records to stricter review.
- **Needs-revision records:** `h2_05_hardware_engineering_embedded_systems_0012` and `b1_07_business_knowledge_finance_0001` were approved by engine-style score 7 but human-flagged for insufficient rationale/caveats.
  - This is a subtle **false-negative-style gap**: the answer was not wrong, but it was underdeveloped for training.

### 3.3 Confidence problems

No record was reviewed with extreme outlier confidence.
The concern here is **license-provenance rejections occurring after engine scoring**, not low-confidence miscalibration.
That gap is best handled as a pre-ingestion provenance gate, not a confidence-function change.

### 3.4 Recommendation for scoring

- Keep `quality_score = 7` threshold behavior for now.
- Add a separate `provenance_clear` signal in the engine/review manifest so license risk is not hidden behind a content-only quality score.
- Consider stricter depth/completeness weighting for categories where human feedback already flagged brevity as a problem.

## 5. Recommendations

### 5.1 Quality engine improvements

1. **Add provenance gating:** separate `license_status` and `provenance_clear` from content quality score so reviewers can see license risk independently.
2. **Add completeness-weighting heuristic for hardware/business topics:** benchmark `answer_substance_length` thresholds by category to reduce `needs_revision` flag volume for short-but-correct knowledge.
3. **Retain constant confidence reporting:** it already surfaced records that are still low-confidence despite approval.

### 5.2 Future review checklist updates

1. **Clarify brevity policy:** explicitly state when short training-relevant facts are acceptable vs incomplete.
2. **Add provenance triage question:** before content scoring, first confirm license/commercial-use clearance; if unclear, route to `needs_investigation` rather than `reject` when content is otherwise valid.
3. **Add depth rubric by category:** include reviewer examples of acceptable and insufficient rationale for hardware and business records.
4. **Add explicit license-handling decision branch:** define when a reviewer should change decision versus add an evidence note requesting legal/source review.

### 5.3 Dataset acquisition improvements

1. **Hard-block known problematic sources** for commercial Atlas pipelines until clearance is documented in `metadata/source_registry.json`.
2. **Prioritize permissive-license replacements** for StackExchange-backed training records after confirming compatible attribution/use terms.
3. **Apply provenance prefiltering before QA scoring** so the quality engine only sees cleared or tentatively cleared sources.
4. **Track rejection taxonomy in metadata:** record rejection class in source registry to enable cohort-level acceptance-rate improvements instead of record-level fixes.
