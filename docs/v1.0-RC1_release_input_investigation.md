# v1.0-RC1 Release Input Investigation

**Status:** COMPLETE — discrepancy fully reconciled
**Date:** 2026-07-31
**Trigger:** release execution found `raw/generated/` shards do not match the frozen manifest

## TL;DR

`review_queue/approved.jsonl` (20 GB) is the **authoritative release dataset** — its
per-category record counts match the frozen v1.0-RC1 manifest **exactly**
(9,893,844 records across 9 categories). The `raw/generated/*_atlas.jsonl`
shards are a **pre-review extraction corpus** and must NOT be used as the
release input.

## Findings

### 1. Manifest is internally consistent on category counts

| Source | Total | Matches manifest? |
|---|---|---|
| `metadata/releases/v1.0-RC1_release.json` `by_category` sum | 9,893,844 | — |
| `review_queue/approved.jsonl` | 9,893,844 | ✅ exact per category |
| `raw/generated/*_atlas.jsonl` (311 shards) | 9,185,508 | ❌ differs; **0 PA records** |
| Manifest `sources` block sum | 8,873,844 | ⚠️ stale/approx (by_category is authoritative) |

`approved.jsonl` category counts match the manifest exactly:
`01:1,000,613 02:1,375,050 03:1,039,979 04:1,066,501 05:1,090,289 06:1,249,899 07:1,066,944 08:1,004,557 09:1,000,012`

### 2. approved.jsonl contains two record shapes

- **8,350,296 full records** — complete canonical records with `messages`,
  `source`, `quality_score`, etc. (includes all 1,000,000 personal-assistant records)
- **1,543,548 review stubs** — index entries only (`id`, `category`,
  `subcategory`, `quality_score`, `license`, verification fields; **no `messages`**)

### 3. Stub content is fully resolvable (0 unresolved)

| Stub source | Count |
|---|---|
| Content inline in `approved.jsonl` | 8,350,296 |
| Stub IDs found in `raw/generated/` shards (join by ID) | 1,543,298 |
| Stub IDs found in pilot/curated sources (250) | 250 |
| **Total resolved** | **9,893,844** ✅ |

The 250 pilot-era stubs (e.g. `m1_04_ai_machine_learning_rag_0007`,
`01_foundation_communication_0002`) resolve from:
`curated/v0.1/data/pilot_candidates.jsonl`, `curated/v0.2/data/*.jsonl`,
`raw/pilot/seed.jsonl`, `review/v0.2/batch_001_input.jsonl` — all verified to
contain full `messages`.

### 4. Why the shards are NOT the release input

- 7,641,557 shard IDs are **not in approved** (rejected/pending/never-reviewed
  records would leak into the release)
- **Zero** `09_personal_assistant` records exist in the shards
- Per-category counts diverge (e.g. shards have 1.9M `06_science_engineering`
  vs 1.25M approved — shards include unapproved OpenWebMath/wiki extras)
- Compressing shards alone → `verify_release.py` fails
  (`counts:total-vs-release` 9,185,508 vs 9,893,844)

## Correct release construction

Release records = `approved.jsonl` (authority, 9,893,844) with content joined:

1. Inline content (8,350,296 records)
2. Shard content by ID (1,543,298 stub records)
3. Pilot/curated content (250 stub records)

Category routing must use the **approved record's `category` field**, not the
shard's, so per-category counts stay manifest-exact.

## Recommendations

1. Add a `stage_release` / join mode to the release pipeline (or a dedicated
   `join_release.py`) that streams `approved.jsonl`, joins stub content from
   shards + pilot sources, and writes per-category canonical JSONL for
   compression.
2. Keep `verify_release.py` as the gate: it must see exactly 9,893,844 records
   and manifest-exact per-category counts.
3. Update `docs/huggingface_release_pipeline.md` input section: the source of
   truth is `review_queue/approved.jsonl`, not `raw/generated/`.
4. Do NOT delete `approved.jsonl` — it is the canonical approved record index.
