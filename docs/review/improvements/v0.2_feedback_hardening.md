# Atlas v0.2 Review Feedback Hardening

**Status:** Recommendation Draft  
**Trigger:** Atlas v0.2 Review Batch 001 — Human Feedback  
**Scope:** Improve future review quality and gating without changing dataset records, review decisions, or v0.2 release state.  
**Constraint:** This document proposes operational changes only. Batch 001 remains authoritative and unchanged. v0.2 release remains blocked.

---

## 1. Provenance Gate Proposal

Batch 001 showed that the dominant failure mode was **provenance and license risk**, not answer correctness. Five of five rejected records were rejected on source or commercial-clearance grounds. To prevent avoidable rework, future candidates should pass explicit provenance checks before quality evaluation or human review.

### 1.1 Source Verification

Require the following fields to be present and populated in review-ready records:

- `source.name` — canonical upstream source name
- `source.id` — stable registry identifier or primary/release identifier
- `source.url` — direct reference URL when available
- `source.date` — ISO-8601 date in `YYYY-MM-DD` on ingestion artifacts, if known
- `pipeline_stage` — upstream stage at which the record originated
- `review_state` — current review lifecycle state

Verification pass criteria:
- Source is recorded in `metadata/source_registry.json` with `status = accepted` or `review`.
- Source is **not** recorded as `status = rejected`.
- For `review` sources, continued access and license terms can be verified from upstream documentation.

### 1.2 License Verification

Use existing script behavior as the canonical standard:
- `scripts/validate_dataset.py` hard-fails on `license == "unknown"`.
- Reuse `is_denied_license()` for ambiguous or problematic license strings.
- Do not manually parse license strings outside scripted checks.

Ongoing license handling should remain aligned with `docs/source_policy.md`:
- NC, proprietary, all-rights-reserved, and ambiguous sources are hard-rejected.
- CC-BY-SA and RAIL-M require explicit attribution and/or share-alike tracking before use.
- Share-alike or access-restricted sources must carry dedicated provenance notes if included.

### 1.3 Attribution Requirements

When a permitted but conditional source is used:
- Record explicit attribution for CC-BY-SA-style licenses.
- Document RAIL-M obligations and any restricted subsets in the ingestion runbook or record-level metadata.
- If attribution details are missing or non-reproducible, reject from review until cleared.

### 1.4 Rejection Conditions

Reject a record during review when any of the following are true:
- Source registry shows `status = rejected`.
- License is NC, proprietary, all-rights-reserved, unknown, or otherwise denied under current policy.
- Source attribution or access terms cannot be confirmed from upstream documentation.
- The source relies on ToS-violating scrapes or datasets without a verifiable usage license.

Preferred action:
- Use `needs_revision` or `needs_investigation` when content quality is otherwise acceptable but provenance is unresolved.
- Use `rejected` when the source itself is disallowed.

## 2. Category Review Rubric

Batch 001 found two categories with **completeness** issues rather than factual errors:
- Hardware records were technically correct but underdeveloped.
- Business records lacked operational caveat coverage.

The rubric below adds depth requirements to improve future training usefulness.

### 2.1 Hardware Engineering

Acceptable hardware answers must include:
- System context and intended use case
- Tradeoff language, such as performance, power, cost, or real-time constraints
- Operational detail that helps a learner apply the concept

Short-form facts are acceptable only when they represent canonical, relationship-based knowledge. Bare definitions without context are usually `needs_revision`.

Examples:
- Acceptable: distinction between bare-metal and RTOS scheduling semantics, including use-case implications
- Insufficient: one-line shorthand with no operational consequence or caveat

### 2.2 Business Knowledge

Acceptable business answers must include:
- Economic or decision rationale near the concept
- Concrete numeric or structural context when formulas, timelines, or pricing relationships are involved
- Practical caveat when assumptions matter

Examples:
- Acceptable: time value of money with formula plus explanation of rate/inflation/horizon effect
- Insufficient: acronym or formula without operational or business consequence

### 2.3 Software Engineering

Current feedback indicates that source verification matters more than completeness for software engineering. Prioritize the following in order:

1. **Source verification first:** confirm registry status, license clarity, and attribution.
2. **Correctness second:** answers should be factually coherent with accepted practices.
3. **Completeness third:** preferred depth includes example evidence, edge case awareness, or operational constraints.

For software engineering, prefer `rejected` when source provenance fails before penalizing answer depth.

## 3. Reviewer Checklist Update Proposal

Use this checklist during human review. Records that fail early gate items should not advance to scoring.

1. **License check**
   - Confirm registry status and license term from source registry and record metadata.
   - Confirm `is_denied_license()` behavior aligns with policy.
   - If status is `rejected`, `review` with missing terms, or license is unresolved, stop here.

2. **Source quality**
   - Prefer authoritative documentation, canonical project sources, or accepted educational content.
   - For software engineering, community-copied content or crowdsourced answers require stronger evidence than official documentation.
   - If source quality is borderline, prefer `needs_revision` over provisional approval.

3. **Answer completeness**
   - Confirm the answer addresses the question without leaving out operative detail.
   - Verify category-specific depth guidance from Section 2.
   - Short canonical facts are acceptable; shorthand omissions of operational context are not.

4. **Training usefulness**
   - Confirm the record teaches a transferable concept or reusable skill.
   - Confirm it does not consist of fragments that require external context to become useful.
   - If usefulness is low, prefer `needs_revision` over approval.

## 4. Pipeline Positioning

Repair provenance issues upstream, before record evaluation. Future review-ready cohorts should follow this order:

1. **License Gate**
   - Run scripted license checks before any content scoring.
   - Reject or quarantine records with denied, unknown, or uncertain licenses.
   - Preserve rejected records only for audit and re-evaluation.

2. **Provenance Check**
   - Validate source registry entries, IDs, attribution fields, and access documentation.
   - Confirm source status is `accepted` or `review` with verifiable terms.
   - Move unresolved-source records to investigation before human review.

3. **Quality Evaluation**
   - Run content scoring and confidence estimation only after records clear upstream gates.
   - Use category-aware completeness weighting where human review return history supports it.

4. **Human Review**
   - Apply the reviewer checklist from Section 3 only to records that already passed License Gate and Provenance Check.
   - Record provenance and completeness findings separately in review decision fields.
