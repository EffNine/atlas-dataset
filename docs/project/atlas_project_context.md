## 1. Executive Summary

### 1.1 What Atlas Is

Atlas is a **model-agnostic, long-term knowledge foundation** for training and evaluating 8B-class large language models (LLMs). It is a governed, deterministic, versioned dataset factory that transforms raw knowledge into production-grade training datasets.

Atlas is not a dataset for one model. The canonical storage format is plain JSONL; model-specific formats (ChatML, Alpaca, ShareGPT, etc.) are generated downstream by converters and never stored as the source of truth. This design decouples the data asset from any single model's chat template or tokenizer, making the dataset durable across model generations.

### 1.2 Why Atlas Exists

The AI industry produces many datasets, but most share common failure modes:

- **Model coupling** — datasets are formatted for a specific model's chat template and become stale when the model is superseded.
- **Non-reproducibility** — processing steps are ad-hoc, undocumented, or depend on manual operations that cannot be repeated.
- **Weak governance** — licensing, provenance, and quality checks are afterthoughts, making datasets risky for commercial use.
- **No versioning** — datasets ship as blobs with no release history, no changelog, and no audit trail.
- **No recovery path** — pipeline failures mid-ingestion force full restarts.

Atlas solves all of these by design.

### 1.3 Problems Atlas Solves

| Problem | Atlas Solution |
|---|---|
| **Model lock-in** | Canonical JSONL storage; model formats generated by config-driven converters |
| **Unreproducible builds** | Every pipeline step is scripted, deterministic, and checksum-verified |
| **License risk** | Denied-license gate at every boundary; provenance chain on every record |
| **No audit trail** | Lifecycle state machine records every transition with timestamp and actor |
| **Manual governance** | Automation layer runs quality, provenance, revision, validation, and approval gates |
| **Lost knowledge** | Raw sources preserved immutably; lineage traces every record to its origin |
| **Fragile pipelines** | State machine persists state to disk; failed stages can be retried independently |

### 1.4 Project Goals

1. **Reproducible dataset generation** — every release is a named, checksummed, verifiable snapshot that can be rebuilt from raw sources.
2. **Commercial-safe licensing** — only permissively-licensed sources enter the curated dataset; denied-license classes are blocked at every gate.
3. **Human-in-the-loop governance** — automated checks catch structural and quality issues; human reviewers hold final authority over dataset releases.
4. **Deterministic processing** — identical inputs always produce identical outputs across the entire pipeline.
5. **Modular extensibility** — new source types, cleaning steps, quality dimensions, and model targets are additive — no existing code is modified.
6. **Quality over quantity** — the curated dataset prioritises verified, high-scoring records over volume.

### 1.5 Long-Term Vision

Atlas will become a **production-grade dataset factory** — a single, automated pipeline that takes raw sources from discovery through acquisition, cleaning, transformation, quality scoring, provenance verification, human approval, and release. The factory is deterministic, auditable, and idempotent. It supports plugin-based source adapters, parallel processing, incremental updates, and distributed execution. It is designed to be the canonical data foundation for all future model training at the organization.

> **The dataset is the long-term asset. Models are replaceable.**

## 2. Project Philosophy

### 2.1 Governance-First

**Principle:** Governance is not an afterthought layered on top of data processing — it is the foundation upon which all data operations are built.

**Why:** A dataset without governance is a liability. Licensing violations, missing provenance, and unaudited quality issues expose the organisation to legal risk and undermine the dataset's value for training. Atlas bakes governance into the pipeline architecture: the state machine enforces mandatory human approval before release, license gates reject denied sources at every boundary, and the lifecycle tracker immutably records every state transition.

### 2.2 Human-in-the-Loop

**Principle:** Automated checks catch machine-detectable issues (schema violations, missing fields, low quality scores). Human reviewers hold final authority over dataset releases and content decisions.

**Why:** Quality scoring algorithms cannot judge factual correctness, tone appropriateness, or strategic fit. The approval gate is hard-coded into the state machine: the `VALIDATION → RELEASED` transition is forbidden — the pipeline must pass through `WAITING_HUMAN_APPROVAL` first. The orchestrator refuses to release without a matching `ApprovalRequest` in `APPROVED` state.

### 2.3 Immutable Datasets

**Principle:** Once a dataset is released, it is never modified. Corrections create a new version (v0.2, v1.0, etc.).

**Why:** Reproducibility of training experiments requires that a model trained on "Atlas v0.1" always uses the same data. Pipeline agents never write to `curated/`, `raw/`, `review_queue/`, or `training_views/`. Only the Release Builder creates new artifacts, always in new directories.

### 2.4 Deterministic Processing

**Principle:** Given the same input and same configuration, every pipeline stage produces the same output.

**Why:** Non-deterministic pipelines produce different results on each run, making it impossible to verify fixes, audit outputs, or trust release artifacts. All agents sort inputs before processing; checksums are computed on sorted, serialized JSON; random number generators are seeded with fixed values when randomness is needed.

### 2.5 Reproducible Releases

**Principle:** Every release can be rebuilt from source inputs using only the pipeline code and configuration.

**Why:** If a model training run needs to be replicated two years later, the pipeline must still produce the same dataset from the same raw data. Every pipeline stage records its version and configuration in metadata. Releases include the pipeline version and all parameter values used.

### 2.6 Provenance Before Convenience

**Principle:** Every record carries its complete provenance chain — where it came from, what license it has, every processing step applied.

**Why:** Governance, licensing compliance, and auditability depend on knowing a record's origin. Without provenance, a dataset cannot be legally used for training. The Canonical Schema requires a `lineage` field; the Provenance Agent validates completeness before records advance through the pipeline.

### 2.7 Fail-Closed Safety

**Principle:** When state is uncertain or required inputs are missing, the pipeline refuses to proceed rather than making assumptions.

**Why:** A dataset with corrupted governance metadata is worse than no dataset. The AcquisitionAgent refuses to acquire packets with missing human decisions; the pipeline refuses to release without human approval; the state machine rejects invalid transitions with clear error messages.

### 2.8 Modular Architecture

**Principle:** Every pipeline stage is a standalone agent with a well-defined interface and no shared mutable state.

**Why:** Modularity enables independent development, testing, and replacement of any stage. A better quality scoring algorithm can be swapped in without touching the rest of the pipeline. A stage can fail without crashing the others. All agents inherit from `BaseAgent` and communicate only through `AgentResult` data dicts.

### 2.9 Separation of Acquisition and Governance

**Principle:** Governance stages (quality, provenance, validation, approval) are separate from transformation stages (extract, normalize, clean, transform, build views).

**Why:** Governance checks must be independent of data formats so they apply uniformly. Transformation stages can be swapped without affecting governance. This separation prevents a transformation bug from silently corrupting governance metadata. Governance agents live in `scripts/automation/`; future transformation stages will live in their own modules.

### 2.10 Stdlib-First Where Practical

**Principle:** Prefer Python standard library over external dependencies unless there is a compelling performance or correctness reason.

**Why:** Minimises dependency management, CI setup complexity, and supply-chain risk. Existing agents use `json`, `hashlib`, `pathlib`, `collections`, `dataclasses`, `abc`, and `re` from stdlib. External dependencies like `jsonschema` or `datasets` are used only in specialised stages where stdlib alternatives don't exist, and are wrapped behind importable interfaces that gracefully degrade when absent.

### 3.3 Architecture Governance Layering

The codebase follows a strict dependency layering model defined in `docs/governance/atlas_architecture_governance.md`. Dependencies flow **downward only**.

```
Layer 1 — Foundation (stdlib-only, no project imports)
  ├── atlas_constants.py       — enums, license functions, type definitions
  ├── atlas_schema.py          — field sets, patterns, validation helpers
  └── atlas_paths.py           — path discovery and construction

Layer 2 — Validation & Lifecycle (imports Layer 1 only)
  ├── validate_dataset.py
  ├── validate_knowledge_object.py
  ├── quality_score.py
  └── acquisition_engine/lifecycle.py

Layer 3 — Engine & Release (imports Layers 1 + 2)
  ├── acquisition_engine/*.py  (except lifecycle.py, which is Layer 2)
  └── payload_resolver.py

Layer 4 — CLI & Tooling (imports Layers 1, 2, 3)
  ├── atlas.py
  └── standalone scripts (clean, convert, dedup, eval, etc.)

Layer 5 — Tests & Standalone (may import any layer)
  └── tests/
```

**Enforcement:** Violations are detected automatically by `scripts/validate_architecture.py`. No non-documentation change may be merged with violations.

**Ownership boundaries** (no module may redefine another's domain):
- `atlas_schema.py` owns all field lists, patterns, and schema validation functions.
- `atlas_constants.py` owns all enums, license checks, and type definitions.
- `atlas_paths.py` owns all path construction.
- `quality_score.py` owns scoring logic.
- `release.py` owns release lifecycle and gates.
- `lifecycle.py` owns lifecycle state transitions.

### 4.2 Stage Descriptions

#### 4.2.1 Source Registry

The source registry (`metadata/source_registry.json`) is the authoritative inventory of all candidate, accepted, review, and rejected sources. Every potential data source is recorded here **before** any data is ingested. This ensures no unvetted source enters the pipeline.

**Key fields:** `id`, `name`, `url`, `category`, `license`, `tier`, `status`, `scores`, `recommendation`, `notes`.

**Status values:** `candidate` → `accepted` | `review` | `rejected`.

**Governance:** Rejected sources (`status: rejected`) are preserved for auditability but are never promoted into curated data. Changes to the registry require an Architecture Decision Record.

#### 4.2.2 Acquisition Manifest

The acquisition manifest defines how vetted sources are split into acquisition packets for ingestion. Each packet has a batch ID, source references, and acquisition parameters. This provides a reproducible plan for what data enters the pipeline and in what order.

#### 4.2.3 Human Review (Acquisition Decisions)

A human reviewer examines source candidates from the registry and makes approval decisions: `APPROVE`, `DEFER`, or `REJECT`. These decisions are recorded in `metadata/acquisition_human_decisions.json`. Only APPROVED packets proceed to the AcquisitionAgent.

#### 4.2.4 AcquisitionAgent

The AcquisitionAgent reads human decisions and the acquisition manifest, validates them against the source registry, and records what should be acquired. It operates in two modes:

- **dry-run** — reports planned acquisitions and skipped packets with reasons, without writing anything.
- **acquire** — creates acquisition logs in `metadata/acquisition_logs/` and records checksums.

**Safety guarantees:**
- Only APPROVED decisions are processed; DEFER and REJECT are skipped.
- Unknown or absent human decision blocks acquisition (fail-closed).
- Rejected-source registry entries are never acquired.
- Dataset roots (`curated/`, `review_queue/`, `training_views/`, `raw/`) are never mutated.

#### 4.2.5 Quality Agent

The Quality Agent scores every record on 7 dimensions (accuracy, completeness, technical correctness, clarity, usefulness, originality, relevance). Each dimension is scored 0–1, weighted, and combined into a final quality score (integer 1–10) with a confidence level (1–5). Records below configurable thresholds are flagged for revision.

#### 4.2.6 Provenance Agent

The Provenance Agent wraps the existing `ProvenanceResolver` (817 lines of production code) via an adapter pattern. It classifies records by resolution status (resolved, unresolved, needs_review). Unresolved records are flagged for human attention.

#### 4.2.7 Revision Agent

The Revision Agent generates structured, actionable revision proposals from quality evaluation findings. It maps low dimension scores to specific improvement suggestions (e.g., "low completeness" → "add missing explanation"). Never modifies dataset records — writes proposals to `metadata/pipeline_revisions/`.

#### 4.2.8 Validation Agent

The Validation Agent performs comprehensive structural validation by delegating to existing production validators:

- `validate_dataset.py` — structural errors, JSON Schema validation
- `validate_knowledge_object.py` — knowledge-object-specific validation
- `atlas_constants.py` — license gate compliance
- Duplicate ID and content detection (normalized SHA-1)
- Strict curated gate (`quality_score >= 7`, `verified=True`)

No dataset files are written — only read-only analysis.

#### 4.2.9 Approval Gate

The Approval Gate is the mandatory human sign-off point. No pipeline reaches `RELEASED` without explicit human approval. The state machine enforces this at two levels:

1. **Orchestrator level** — checks `approval_gate.is_releasable()` before permitting the `WAITING_HUMAN_APPROVAL → RELEASED` transition.
2. **State machine level** — the `VALIDATION → RELEASED` transition is not a valid transition; the pipeline must pass through `WAITING_HUMAN_APPROVAL`.

**Audit trail:** Every approval/denial is recorded with `decided_by`, `role`, `timestamp`, and `comments`.

#### 4.2.10 Release Manager

The Release Manager is the final gate. It verifies ALL required gates pass before creating a release artifact:

| Gate | Condition |
|---|---|
| Quality | 100% records have `quality_score >= 7` |
| Provenance | No unresolved records |
| Revision | No critical revision flags |
| Validation | Zero structural/schema/license errors |
| Human Approval | Matching `APPROVED` ApprovalRequest |

Creates release artifacts in `metadata/releases/` with:
- Release manifest (version, type, statistics, gate results, checksums)
- Semantic diff from previous release
- Hash chain linking release to genesis
- Content signature

#### 4.2.11 Training Views

Training views are generated, disposable, model-specific renderings of the canonical dataset. The Training View Engine (`scripts/training_view_engine/`) supports:

- **Views by model family** (Qwen ChatML, Llama Instruction, DeepSeek format)
- **Filtered packs** (category, quality threshold, knowledge type)
- **Evaluation sets** (held-out splits frozen at release time)

**Rule:** Training views are never the source of truth. The canonical JSONL dataset in `curated/` is the single source of truth.

### 4.3 Pipeline State Machine

The automation layer's state machine governs pipeline progression through exactly 9 states:

```
INGESTED ──→ QUALITY_CHECK ──→ PROVENANCE_CHECK ──→ CONTENT_REVISION
    ──→ VALIDATION ──→ WAITING_HUMAN_APPROVAL ──→ READY_FOR_RELEASE
    ──→ RELEASED

Stopping states:
    ├── FAILED            (pipeline halted on error)
    └── RELEASE_REJECTED  (human denied release)
```

**State machine rules:**
1. **Forward-only** — transitions are irreversible; no backward movement.
2. **Sequential** — states cannot be skipped.
3. **Terminal** — `RELEASED` has no outgoing transitions.
4. **Human approval mandatory** — the pipeline blocks at `WAITING_HUMAN_APPROVAL` until a human approves.
5. **Persistence** — state is saved to `metadata/pipeline_state/<pipeline_id>.json` on every transition.

## 7. Data Lifecycle

### 7.1 Lifecycle States

Every record in Atlas progresses through a formal lifecycle with 8 states:

```
raw → processing → curated → review → approved → released → archived
  ↓                                                        ↓
  └→ rejected                                     rejected ←┘
```

| State | Definition | Mutability |
|---|---|---|
| **raw** | Original source artifact, ingested from external or generated source | Immutable |
| **processing** | In pipeline — cleaning, deduplication, scoring, transformation active | Regenerable |
| **curated** | Passed pipeline gates (quality, license, schema) but not yet human-approved | Append-only |
| **review** | In explicit human review queue | Read-only (reviewers attach metadata, not edits) |
| **approved** | Human-approved for release | Append-only |
| **released** | Included in a frozen release artifact | Immutable |
| **archived** | Superseded or deprecated; retained for lineage | Immutable |
| **rejected** | Did not pass gates or review; may re-enter pipeline only with recorded rationale | Re-enter via rejection → raw |

### 7.2 Valid Transitions

| From | To |
|---|---|
| raw | processing, rejected |
| processing | curated, rejected, raw |
| curated | review, processing, rejected |
| review | approved, rejected, needs_revision |
| needs_revision | review, rejected, curated |
| approved | released, review |
| released | archived |
| archived | — |
| rejected | raw |

Any transition outside this set is invalid and must fail validation. Every transition is recorded in `metadata/lifecycle_state.json` with `from`, `to`, `timestamp`, `source`, and `reason`.

## 8. Automation Layer

### 8.1 Architecture Overview

The automation layer transforms Atlas from a manually-operated workflow into an automated pipeline with mandatory human approval before release. It consists of:

- **Statemachine** — formal FSM governing pipeline progression
- **Orchestrator** — workflow coordinator owning the state machine, approval gate, and agents
- **Approval Gate** — human sign-off enforcement
- **Agents** — pluggable pipeline stage executors
- **Base Agent Interface** — abstract contract for all agents
- **Failure Recovery** — targeted retry without full pipeline restart
- **CLI** — automation runner for operator interaction

```
                    ┌─────────────────────────────────────────────┐
                    │            Pipeline Orchestrator             │
                    └────────────────────┬────────────────────────┘
                                         │
                    ┌────────────────────┼────────────────────┐
                    │                    │                    │
                    ▼                    ▼                    ▼
         ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
         │   State Machine   │  │  Approval Gate    │  │     Agents       │
         │   (FSM)           │  │  (Human Gate)     │  │  (Executors)     │
         └────────┬─────────┘  └────────┬─────────┘  └────────┬─────────┘
                  │                      │                     │
                  ▼                      ▼                     ▼
         ┌──────────────────────────────────────────────────────────┐
         │              Persistence Layer (metadata/)               │
         │    pipeline_state/<id>.json    pipeline_approvals.json   │
         └──────────────────────────────────────────────────────────┘
```

### 8.2 State Transitions

The pipeline progresses through exactly 7 mandatory states in strict forward order:

```
INGESTED → QUALITY_CHECK → PROVENANCE_CHECK → CONTENT_REVISION
    → VALIDATION → WAITING_HUMAN_APPROVAL → RELEASED
```

Plus two stopping states:
- `FAILED` — entered when a critical agent fails
- `RELEASE_REJECTED` — entered when human denies release

**Rules:**
1. Forward-only — no backward movement (except retry, which reruns the failed agent then continues forward).
2. Sequential — states cannot be skipped (e.g., `INGESTED → VALIDATION` is invalid).
3. Terminal — `RELEASED` has no outgoing transitions.
4. Human approval mandatory — the orchestrator blocks `RELEASED` unless the approval gate grants sign-off.
5. Persistence on every transition — state saved to `metadata/pipeline_state/<pipeline_id>.json`.

### 8.3 Agent Execution Model

Every agent implements the `BaseAgent` abstract interface:

```python
class BaseAgent(ABC):
    name: str
    description: str

    def __init__(self, root, config=None): ...
    @abstractmethod
    def execute(self, context=None) -> AgentResult: ...
    def validate_config(self) -> list[str]: ...
```

**Execution rules:**
1. Agents run sequentially in pipeline order (quality → provenance → revision → validation).
2. Each agent receives the output of the previous agent as context.
3. Agents may fail (critical) or pass with warnings (advisory).
4. Agent results are collected by the orchestrator for gate evaluation.
5. Agents never modify dataset files — only read and report.

### 8.4 Retry and Resume

When a pipeline enters `FAILED`:

1. **Diagnose** — the failure recovery module identifies the failed agent.
2. **Retry** — `retry()` reruns only the failed agent (scoped per type).
3. **Continue** — on success, the pipeline continues from the retried agent forward.
4. **Persist** — retry history is written to `metadata/pipeline_retries/`.
5. **Limit** — repeated failures stay in `FAILED` (no infinite loop).

**Retry rules:**
- Quality agent fails → retry quality agent only
- Provenance agent fails → retry provenance agent only
- Pipeline does not restart from `INGESTED`
- All retries are logged with timestamps and outcomes

### 8.5 Failure Persistence

All automation state persists to disk under `metadata/`:

| Data | Path |
|---|---|
| Pipeline state | `metadata/pipeline_state/<id>.json` |
| Approval decisions | `metadata/pipeline_approvals.json` |
| Revision proposals | `metadata/pipeline_revisions/<id>/` |
| Retry history | `metadata/pipeline_retries/<id>.json` |
| Agent reports | `tmp/` (gitignored) |

### 8.6 Human Approval

The human approval flow is enforced at two levels:

1. **State machine design** — `WAITING_HUMAN_APPROVAL` is a mandatory state before `RELEASED`. The transition `VALIDATION → RELEASED` is **not valid**.
2. **Orchestrator gate check** — `_advance_pipeline()` checks `approval_gate.is_releasable()` before calling `state_machine.transition_to(RELEASED)`.

**Approval flow:**
```
Pipeline runs automated stages
              │
              ▼
WAITING_HUMAN_APPROVAL (pipeline blocks)
              │
         ┌────┴────┐
         ▼         ▼
    APPROVED     DENIED
         │         │
         ▼         ▼
     RELEASED   RELEASE_REJECTED
```

### 8.7 Release Gates

All gates must pass for a release to proceed:

| Gate | Checked By | Condition |
|---|---|---|
| Quality | Release Manager | 100% records have `quality_score >= 7` |
| Provenance | Release Manager | No unresolved records |
| Revision | Release Manager | No critical revision flags |
| Validation | Release Manager | Zero structural/schema/license errors |
| Human Approval | Release Manager | Matching APPROVED ApprovalRequest |

## 9. Safety Model

### 9.1 Fail-Closed Behaviour

**Rule:** When state is uncertain or required inputs are missing, the pipeline refuses to proceed.

**Enforcement:**
- AcquisitionAgent refuses acquisition without human decisions for every packet.
- Approval gate refuses release without matching APPROVED request.
- State machine rejects invalid transitions (skip, backward, post-terminal).
- Pipeline orchestrator stops on critical agent failures.
- All agents check preconditions before executing.

**Rationale:** A dataset with corrupted governance metadata is worse than no dataset.

### 9.2 Immutable Directories

**Rule:** Pipeline agents never write to dataset source directories.

**Protected directories (never written by automation):**
- `curated/` — dataset release artifacts
- `review_queue/` — review queue items
- `training_views/` — training view files
- `raw/` — raw data sources
- `schemas/` — schema definitions

**Permitted write targets:**
- `metadata/` — all pipeline state and registries
- `tmp/` — temporary reports and intermediate files

**Enforcement:** `atlas_paths.py` defines `APPROVED_WRITE_ROOTS` and `approved_write_paths()`. All agents must use `atlas_paths` for path construction. The self-test framework assert `no-unauthorized-writes` invariant.

### 9.3 Checksum Validation

**Rule:** Every file in a release, pack, or collection has a SHA-256 checksum recorded in an associated registry.

**Enforcement:**
- `checksums_v0.1.json` — dataset-level file checksums
- `engine_checksums.json` — acquisition engine checksums
- Pack manifests include per-file checksums
- Release manifests include checksum registry references
- Semantic diff validates file-level integrity

**Verification:** The Integrity Engine (`scripts/acquisition_engine/integrity.py`) normalizes both list and dict checksum formats and supports `verify()` and `diff_registries()` functions.

### 9.4 Human Approval

**Rule:** No automated pipeline can release a dataset without human sign-off.

**Enforcement:**
- State machine: `VALIDATION → RELEASED` is not a valid transition.
- Orchestrator: checks `is_releasable()` before permitting release.
- Approval Gate: records every decision with `decided_by`, `role`, `timestamp`, `comments`.
- Multiple authorisation levels: REVIEWER, MAINTAINER, ARCHITECT roles.

### 9.5 Audit Trails

**Rule:** Every state change, decision, and failure is recorded with timestamp and actor information.

**Audit logs:**
- Lifecycle state transitions: `metadata/lifecycle_state.json`
- Approval decisions: `metadata/pipeline_approvals.json`
- Pipeline state transitions: `metadata/pipeline_state/<id>.json`
- Acquisition records: `metadata/acquisition_logs/<id>.json`
- Retry history: `metadata/pipeline_retries/<id>.json`
- Release manifests: `metadata/releases/<version>_release.json`

### 9.6 Deterministic Outputs

**Rule:** Given the same input and same configuration, every pipeline stage produces the same output.

**Enforcement:**
- All agents sort inputs before processing.
- Checksums computed on sorted, serialized JSON.
- Random number generators seeded with fixed values.
- AQL queries are deterministic.
- Schema validation is input-deterministic.
- Migration transformations are input-deterministic.

### 9.7 Provenance

**Rule:** Every record in the dataset carries its complete provenance chain.

**Enforcement:**
- Canonical Schema requires a `lineage` field (source, transformations, knowledge_object, curated_dataset, training_view, future_model).
- Provenance Agent validates completeness before records advance.
- Source attribution includes `source_id`, `name`, `url`, `license`, `attribution_text`.
- Rejected sources recorded in `source_registry.json` with `status: rejected`.

### 9.8 Recovery

**Rule:** Pipeline failures are recoverable without restarting from scratch.

**Enforcement:**
- State persists to disk on every transition.
- Failure Recovery supports targeted agent retry.
- Retry history prevents infinite loops.
- Pipeline state can be inspected via CLI (`status` command).
- Manual intervention path exists for unrecoverable failures.

### 9.9 License Safety

**Rule:** No unlicensed or restricted-license data enters the curated dataset or any release.

**Denied license patterns (automatically blocked at all gates):**
- `cc-by-nc*` — non-commercial
- `cc-by-nd*` — no derivatives
- `proprietary`
- `all-rights-reserved`
- `unknown`

**Allowed licenses (with conditions for some):**
- MIT, Apache-2.0, BSD-2/3, CC-BY-3.0/4.0, CC0-1.0, ODC-BY, Public Domain, arXiv non-exclusive license
- CC-BY-SA-3.0/4.0 (requires attribution_text and share-alike tracking)
- BigCode Open RAIL-M (requires permissive-file subsetting and documented obligations)

**Curated-stage rule:** `license` must never be `unknown`. Unresolved unknown records must be rejected or deferred.

## 11. Development Workflow

### 11.1 Git Workflow

Atlas follows a **feature-branch workflow** with the following conventions:

**Branch naming:**
- `feature/<short-description>` — new features
- `fix/<short-description>` — bug fixes
- `docs/<short-description>` — documentation changes
- `refactor/<short-description>` — code refactoring
- `gov/<short-description>` — governance/contract changes

**Branch naming rules:**
- Lowercase only
- Hyphens as separators
- Short, descriptive (50 chars max)
- No trailing slash or period

**Commit conventions:**
- One logical batch per commit
- Prefix with affected area: `feature:`, `fix:`, `docs:`, `refactor:`, `gov:`, `test:`
- Each feature version should be committed separately with its own descriptive message
- When implementing multi-phase features, commit each version individually after tests pass

**Example:**
```
git checkout -b feature/acquisition-agent-v1
# ... implement ...
git commit -m "feature: add AcquisitionAgent v1 with dry-run and acquire modes"
# ... add tests ...
git commit -m "test: add AcquisitionAgent unit tests"
```

### 11.2 Testing Requirements

Before merging any change:

1. **Run self-tests:** `python scripts/atlas.py self-test` — verifies invariants (network isolation, write safety, license gate, manifest validation, schema compliance)
2. **Run architecture validator:** `python scripts/validate_architecture.py` — enforces dependency layering
3. **Run unit tests:** `pytest tests/` — automation layer tests (47 tests), acquisition agent tests, failure recovery tests
4. **Run validation scripts:** validate_dataset, validate_knowledge_object for any affected data

**Test categories:**

| Category | What's Tested |
|---|---|
| State Machine | Initial state, full sequence, invalid transitions, persistence, helpers |
| Approval Gate | Create, approve, deny, persistence, blocking, rescind |
| Pipeline Orchestrator | Initialisation, reset, approval integration, agent sequencing |
| Base Agent | Abstract interface, properties, serialization |
| Failure Recovery | Retry scoping, persistence, max retry enforcement |
| Acquisition Agent | Dry-run, acquire, fail-closed on missing decisions |
| Provenance | Resolution status classification |
| Architecture Governance | Dependency layering compliance |

### 11.3 Code Review Process

1. **Author** runs all tests, self-tests, and architecture validation before requesting review.
2. **Reviewer** checks:
   - Architecture layering compliance (no upward imports)
   - Ownership boundaries respected (no duplicate definitions)
   - New agents inherit from `BaseAgent`
   - No writes to protected directories
   - Determinism preserved (sorted inputs, seeded RNG)
   - Tests cover both success and failure paths
3. **Merge** requires at least one approving review and all CI checks passing.

### 11.4 Release Workflow

1. **Prepare:** Ensure pipeline state is clean (no active pipeline in progress).
2. **Run automated stages:** `python -m scripts.automation_runner run-to-approval --pipeline-id release-vX.Y`
3. **Review:** Examine agent reports — quality scores, provenance status, revision proposals, validation results.
4. **Approve:** `python -m scripts.automation_runner approve --pipeline-id release-vX.Y --reviewer <name> --role REVIEWER`
5. **Release:** `python -m scripts.automation_runner release --pipeline-id release-vX.Y`
6. **Verify:** Check release manifest, stats, and checksums in `metadata/releases/`.

### 11.5 Adding New Data

Follow the contribution workflow:

1. **Source first** — register the source in `metadata/sources.json`.
2. **Ingest raw** — place original files in `raw/<category>/` (immutable).
3. **Clean** — run `scripts/clean_dataset.py` to normalize into canonical form.
4. **Validate** — run `scripts/validate_dataset.py` for schema compliance.
5. **Score** — run `scripts/quality_score.py` for automated quality assessment.
6. **Review** — human reviewer sets `verified=true` after passing all gates.
7. **Promote** — move to `curated/vX.Y/data/` for inclusion in next release.

### 11.6 Architecture Governance Enforcement

Every change must comply with the architecture governance contract:

- **Layer 1** (Foundation): stdlib-only imports; no project module dependencies.
- **Layer 2** (Validation): may import Layer 1; no CLI imports.
- **Layer 3** (Engine): may import Layers 1–2; no CLI imports.
- **Layer 4** (CLI): may import any lower layer; no business logic in CLI.
- **Layer 5** (Tests): may import any layer; must not modify datasets.

Enforced by `scripts/validate_architecture.py` — runs as a pre-merge CI check.

## 12. Future Architecture

### 12.1 Downloader

**When:** v1.6

**Purpose:** Actually download data from external sources instead of only recording the intent.

**Design:**
- **SourceAdapter interface:** abstract `SourceAdapter` with `download(source_ref, target_dir) -> DownloadResult` method.
- **Type-specific adapters:** HuggingFaceAdapter, GitHubAdapter, DocumentationAdapter, StackExchangeAdapter, arXivAdapter.
- **Common policies:** rate limiting, polite crawling, API key management per adapter.
- **Integration:** AcquisitionAgent output feeds into the downloader's work queue.

**Key constraints:**
- All downloads go through the Cache Manager (never re-download).
- Each adapter handles its own auth and protocol.
- Failed downloads are retried with exponential backoff.

### 12.2 Cache Manager

**When:** v1.6

**Purpose:** Prevent redundant downloads and support resumable transfers.

**Design:**
- **Content-addressable store:** files stored by SHA-256 content hash.
- **Resume support:** interrupted downloads resume from last byte (HTTP Range headers).
- **Checksum verification:** every downloaded file verified against source-provided or computed checksums.
- **Retry strategy:** exponential backoff with configurable max retries.
- **Storage budgeting:** configurable max cache size with LRU eviction or manual purge.
- **Cache index:** SQLite or JSON index mapping source references → cached file paths + metadata.

**Location:** `raw/.cache/` — separate from immutable `raw/` storage.

### 12.3 Normalizer

**When:** v1.7

**Purpose:** Convert every extracted record into the Atlas Canonical Schema — the single internal representation.

**Design:**
- Map source-specific field names to canonical fields.
- Convert date formats to ISO 8601.
- Normalize license strings to canonical forms.
- Standardise role names (`human` → `user`, `bot` → `assistant`).
- Ensure every record has required fields: `id`, `source`, `license`, `content`, `created_at`, `lineage`.
- Fail on unmappable required fields (configurable strictness).

### 12.4 Cleaner

**When:** v1.7

**Purpose:** Production-quality cleaning of normalized records.

**Cleaners (composable pipeline):**
| Cleaner | What It Does | Criticality |
|---|---|---|
| **Duplicate Remover** | Content-hash dedup + near-duplicate detection (MinHash/LSH) | HIGH |
| **PII Filter** | Regex-based PII detection (emails, API keys, IPs, SSNs) | HIGH |
| **Malformed Conversation Remover** | Unclosed turns, mismatched roles, empty messages | HIGH |
| **License Metadata Injector** | Add canonical license + attribution + obligations to every record | MEDIUM |
| **Language Validator** | Detect language, filter to target set, flag low-confidence | MEDIUM |
| **Length Filter** | Min/max content length enforcement | LOW |

**Key constraints:**
- Each cleaner is an independent, composable step.
- Cleaners operate on a streaming pipeline (memory-efficient).
- Every cleaning operation is logged for audit.
- Original content is preserved in lineage metadata.

### 12.5 Transformation Engine

**When:** v1.8

**Purpose:** Convert cleaned, normalized content into the five Atlas training record types.

**Target record types:**

```
Documentation  ──→  instruction  (how-to guides, tutorials)
QA             ──→  qa_pair      (question → answer)
Conversation   ──→  conversation (multi-turn dialogue)
Reasoning      ──→  reasoning    (step-by-step logic, chain-of-thought)
Knowledge      ──→  knowledge    (factual knowledge object)
```

**Key constraints:**
- Each transformation is a standalone module with a `transform(record) -> list[TrainRecord]` interface.
- One input record may produce multiple training records.
- Transformations are auditable — provenance chain preserved.
- Unconfident records pass through as-is with `transformation: raw` tag.

### 12.6 Dataset Builder

**When:** v1.8

**Purpose:** Generate model-family-specific training views and evaluation sets from the canonical dataset.

**View types:**
- **Review Queue Views** — `review_queue/` per-batch view of unverified records.
- **Curated Views** — `curated/vX.Y/` versioned, verified, quality-gated snapshots.
- **Training Views** — `training_views/{model}/` formatted per model chat template.
- **Evaluation Sets** — `evaluation/vX.Y/` held-out test sets, benchmark-compatible subsets.

**Key constraints:**
- Views are **generated, not stored** — deterministic outputs from curated data.
- Each model family gets its own subdirectory under `training_views/`.
- Evaluation sets are frozen at release time.

### 12.7 Incremental Updates

**When:** v1.9

**Purpose:** Support delta processing — only re-process sources that changed since the last release.

**Design:**
- Each source tracks a last-processed timestamp or content hash.
- Pipeline detects unchanged sources and skips their processing stages.
- Changed sources flow through the full pipeline.
- Release builds include both new and unchanged records.
- Cache invalidation is source-aware.

### 12.8 Parallel Processing

**When:** v1.9

**Purpose:** Scale the pipeline to handle thousands of sources and millions of records.

**Design:**
- Multi-worker extraction/normalization/cleaning.
- Streaming pipeline mode (process without loading everything into memory).
- Thread-safe cleaners and extractors (shared-state audit required).
- Parallel I/O for cache and disk operations.

### 12.9 Distributed Processing

**When:** Post-v2.0

**Purpose:** Support distributed execution across multiple machines for very large datasets.

**Design:**
- Worker pool model with task queue.
- Distributed cache across machines (shared filesystem or object store).
- Coordinator node managing workflow state.
- Result aggregation from distributed workers.

### 12.10 Plugin Architecture

**When:** Post-v2.0

**Purpose:** Allow third-party extensions to Atlas without modifying core code.

**Design:**
- **Plugin types:** SourceAdapters, Extractors, Cleaners, Transformers, Quality Scorers, Output Formats.
- **Registration:** Plugins register via a declarative manifest in a well-known directory.
- **Discovery:** Plugin manager discovers installed plugins at startup.
- **Sandboxing:** Plugins run with limited filesystem access (cannot write to protected directories).
- **Versioning:** Plugins declare compatibility with specific Atlas versions.

## 13. Known Constraints

### 13.1 Current Limitations

#### 13.1.1 No Download Capability

The current AcquisitionAgent records what *should* be acquired but does **not** perform actual downloads. Data acquisition is a metadata-only operation. Physical download requires the future Downloader subsystem (planned v1.6).

#### 13.1.2 Placeholder Agents

The Quality, Revision, and Validation agents in the automation layer perform real structural checks (score ranges, field presence, license gates) but do not yet integrate with the full production scoring, revision, and validation pipelines. Full integration is scheduled for v1.7–v1.8.

#### 13.1.3 No Training View Production Integration

The Training View Engine (`scripts/training_view_engine/`) exists with generator, filter, manifest, and validator modules, but is not yet integrated with the automation pipeline. Training views are generated manually. Automation-layer integration is planned for v1.8.

#### 13.1.4 No Incremental Updates

Every pipeline run processes all records from scratch. There is no delta detection — unchanged records are re-processed each run. Incremental processing is planned for v1.9.

#### 13.1.5 Single-Threaded Processing

All pipeline stages run sequentially in a single thread. No parallel processing is implemented. Parallelism is planned for v1.9.

#### 13.1.6 Limited Scale

The current architecture is tested with hundreds to low thousands of records. Scaling to millions of records requires streaming pipelines and distributed processing (v1.9+).

#### 13.1.7 No External Notifications

When the pipeline reaches `WAITING_HUMAN_APPROVAL`, there is no mechanism to notify human reviewers (email, messaging, webhook). Operators must manually check pipeline status.

#### 13.1.8 Single Dataset Version at a Time

The pipeline orchestrates a single pipeline ID. Multi-pipeline orchestration (parallel datasets, dependency graphs) is future work.

### 13.2 Intentional Design Decisions

#### 13.2.1 Stdlib-First

Preferring Python standard library over external dependencies is an intentional choice to minimise dependency management, CI complexity, and supply-chain risk. External dependencies are only added when stdlib alternatives don't exist (e.g., `jsonschema` for JSON Schema validation).

**Trade-off:** Some operations that would be simpler with libraries (e.g., HTTP downloads via `requests`) are more verbose with stdlib (`urllib.request`). The trade-off is accepted for the operational simplicity.

#### 13.2.2 File-Based Persistence

Pipeline state is persisted as JSON files on disk rather than in a database. This is intentional: JSON files are human-readable, debuggable, version-controllable, and require no database infrastructure.

**Trade-off:** No ACID transactions, no concurrent write protection, no query capability. These are acceptable for a single-operator pipeline with sequential execution.

#### 13.2.3 Separate Checksum Registries

The dataset (`checksums_v0.1.json`) and engine (`engine_checksums.json`) maintain separate checksum registries. This is intentional: they serve different purposes (dataset integrity vs. engine processing verification) and have different update frequencies.

**Trade-off:** Verification code must handle both formats. The Integrity Engine's `verify()` and `diff_registries()` functions normalise both formats transparently.

#### 13.2.4 Adapter Pattern for Provenance

The ProvenanceAgent wraps the existing `ProvenanceResolver` via adapter rather than rewriting it. This preserves the original tool's 817-line production codebase, its test coverage, its docs, and its CLI integration.

**Trade-off:** The adapter adds a thin abstraction layer. The benefit of zero regression risk outweighs the minor complexity.

#### 13.2.5 Separation of Dataset Versions

Each curated version (`v0.1/`, `v0.2/`, `v1.0/`) is a completely independent directory rather than using symlinks or overlays. This makes each version self-contained and verifiable without reference to other versions.

**Trade-off:** Disk usage grows with each version. The cost is acceptable for the clarity and independence gained.

### 13.3 Non-Goals

The following are explicitly not goals of Atlas:

1. **Not a model runtime** — Atlas produces datasets, not model inference or training.
2. **Not a preference-tuning dataset contract** — unless explicitly declared in a training recipe.
3. **Does not enforce one chat template** — canonical storage is template-agnostic JSONL.
4. **Does not replace upstream source attribution obligations** — users must confirm license use-fit.
5. **Does not guarantee legal advice** — license classification is automated policy enforcement, not legal counsel.
6. **Not a real-time system** — pipeline latency is measured in minutes to hours, not milliseconds.
7. **Not a multi-tenant platform** — single-operator, single-dataset focus.

## 14. Glossary

### A

**Acquisition Manifest**
A JSON file that defines how vetted sources are split into acquisition packets for ingestion. Includes packet IDs, source references, batch metadata, and acquisition parameters. (`metadata/acquisition_manifest_v0.1.json`)

**Acquisition Packet**
A discrete unit of data acquisition defined in the acquisition manifest. Each packet corresponds to a source or source subset and has its own batch ID, human decision, and acquisition log.

**AcquisitionAgent**
An automation pipeline component that enforces the transition from human review decisions to actual data acquisition. Operates in dry-run and acquire modes. Validates against human decisions, acquisition manifest, and source registry.

**ADR (Architecture Decision Record)**
A formal document describing a contract-level architecture decision — context, decision, alternatives, consequences, and compatibility notes. Stored in `docs/adr/`. Required for any contract-level change.

**Agent**
A pipeline stage executor implementing the `BaseAgent` interface. Each agent performs a specific function (quality scoring, provenance verification, revision generation, validation, acquisition).

**Approval Gate**
The automation component that enforces mandatory human approval before dataset release. Records all decisions with timestamp and actor information.

**AQL (Atlas Query Language)**
A deterministic query language for selecting, filtering, aggregating, and ordering dataset objects. Supports tag-style (`category:01_foundation quality>=7`) and SQL-style (`SELECT * WHERE category = "01_foundation"`) syntax.

### B

**BaseAgent**
Abstract base class that all pipeline agents must implement. Defines `execute(context) -> AgentResult` as the primary interface.

### C

**Calibration**
The process of comparing automated quality scores against structured human review to measure accuracy, bias, and confidence. Produces a calibration baseline that gates bulk ingestion.

**Canonical Schema**
The single, model-agnostic JSON Schema that defines the structure of all Atlas records. Has two levels: `dataset_schema.json` (base) and `knowledge_object_schema.json` (full superset).

**Collection**
A named aggregation of knowledge packs forming a higher-level bundle. Includes aggregate statistics and collection-level checksums. Stored under `knowledge_packs/collections/`.

**Curated**
The lifecycle state for records that have passed all automated pipeline gates (quality, license, schema) but have not yet been human-approved for release.

**Curated Dataset**
A versioned, immutable snapshot of reviewed and verified records stored under `curated/vX.Y/`. This is the primary output of the Atlas pipeline.

### D

**Deterministic Processing**
The property that given the same input and same configuration, every pipeline stage produces exactly the same output. Enforced by sorting inputs, seeding RNGs, and deterministic algorithms.

### F

**Fail-Closed**
A safety principle where the pipeline refuses to proceed when state is uncertain or required inputs are missing, rather than making assumptions.

**Failure Recovery**
The automation component that supports targeted retry of failed pipeline agents without restarting from the initial state.

### G

**Gate**
A quality or governance checkpoint that must pass for a pipeline stage to complete. Examples: quality gate, license gate, schema gate, verification gate, approval gate.

### H

**Hash Chain**
A sequence of release hashes where each release records the hash of the previous release, forming an auditable chain from the genesis release to the current release.

**Human Review**
The process by which human evaluators examine data sources, quality scores, and dataset candidates to make approval decisions. Required at multiple points in the pipeline.

### I

**Idempotent**
The property that running the same pipeline stage multiple times produces the same result as running it once. Enables safe retry and incremental updates.

**Immutable Dataset**
A dataset that, once released, is never modified. Corrections create a new version. Enforced by write protection on `curated/`, `raw/`, and other data directories.

**Integrity Engine**
The subsystem responsible for tamper-evident checksum verification and hash-chain audit. Normalises checksum registry formats and supports verification and diff operations.

### K

**Knowledge Collection**
See **Collection**.

**Knowledge Object**
The full canonical record shape in Atlas, including messages, lineage, attribution, verification, and quality fields. Defined by `schemas/knowledge_object_schema.json`.

**Knowledge Pack**
A focused subset of curated records packaged as an independent, verifiable unit. Includes data file, manifest, and checksums.

### L

**License Gate**
An automated check that rejects records with denied, unknown, or ambiguous licenses. Enforced at curation, validation, and release boundaries.

**Lifecycle**
The formal state machine governing record progression through 8 states (raw → processing → curated → review → approved → released → archived, plus rejected).

**Lifecycle Manager**
The system responsible for tracking and validating record state transitions. Implementation in `scripts/acquisition_engine/lifecycle.py`.

**Lineage**
The provenance chain attached to every record, tracing it from source through all transformations to its final form. Required fields: source, transformations, knowledge_object, curated_dataset, training_view, future_model.

### M

**Manifest**
A JSON file describing the contents and metadata of a dataset version, release, pack, or collection. Includes statistics, checksums, and configuration.

**Migration**
A versioned, named transformation that updates records from one schema version to another. Migrations have up/down semantics and are recorded in an applied ledger.

**MinHash/LSH**
A locality-sensitive hashing technique used for near-duplicate detection in the deduplication subsystem.

### N

**Normalizer**
A future component (v1.7) that converts extracted records from source-specific formats into the Atlas Canonical Schema.

### O

**Orchestrator**
See **Pipeline Orchestrator**.

### P

**Packet**
See **Acquisition Packet**.

**Pipeline**
The end-to-end automated workflow that processes raw data through quality, provenance, revision, validation, approval, and release stages. Governed by the state machine.

**Pipeline Orchestrator**
The automation component that owns the state machine, approval gate, and all agents. Sequences pipeline stages and manages gate transitions.

**Provenance**
The complete origin and processing history of a record, including source identification, license, attribution, and every transformation applied.

**Provenance Agent**
The automation agent that validates record provenance completeness by wrapping the `ProvenanceResolver` via adapter pattern.

**ProvenanceResolver**
A production component (817 lines) that resolves record provenance against the source registry. Wrapped by the Provenance Agent.

### Q

**Quality Agent**
The automation agent that performs 7-dimension quality scoring on every record, computing aggregate statistics and reporting issues.

**Quality Calibration**
The process of comparing automated quality scores against structured human review to calibrate and validate the scoring model. Results are frozen as a baseline before bulk ingestion.

**Quality Engine**
The subsystem responsible for automated 7-dimension quality scoring. Defined by `scripts/quality_score.py` and formalised in `docs/specs/quality_engine_spec.md`.

**Quality Score**
An integer from 1–10 representing the overall quality of a record. Computed as a weighted sum of 7 dimensions. Acceptance threshold for curated: `>= 7`.

### R

**Raw**
The initial lifecycle state for original source artifacts. Raw files are immutable — never edited in place.

**Recipe**
See **Training Recipe**.

**Registry**
See **Source Registry**.

**Release**
A frozen, versioned snapshot of the dataset at a point in time. Includes manifest, statistics, checksums, and hash chain linkage.

**Release Manager**
The automation component that verifies all gates pass and creates versioned release artifacts in `metadata/releases/`.

**Revision Agent**
The automation agent that generates structured improvement proposals for records with low quality scores.

**Revision Proposal**
An actionable improvement suggestion generated by the Revision Agent. Includes field name, current content, proposal type, and description. Never modifies records directly.

### S

**Self-Test**
A deterministic, network-isolated invariant validation suite. Covers schema compliance, license correctness, write safety, dependency checks, and more.

**Semantic Diff**
A comparison between two dataset versions that identifies breaking and non-breaking changes. Used to assess upgrade impact.

**Source Adapter**
A future component (v1.6) that handles downloading data from a specific source type (HuggingFace, GitHub, arXiv, etc.). Each adapter implements a common `download()` interface.

**Source Registry**
The authoritative machine-readable inventory of all data sources. Records candidate, accepted, review, and rejected sources with full metadata. (`metadata/source_registry.json`)

**State Machine**
The finite state machine governing pipeline lifecycle progression (INGESTED → QUALITY_CHECK → PROVENANCE_CHECK → CONTENT_REVISION → VALIDATION → WAITING_HUMAN_APPROVAL → READY_FOR_RELEASE → RELEASED, plus FAILED and RELEASE_REJECTED). Implementation in `scripts/automation/state_machine.py`.

### T

**Training Recipe**
A declarative, non-data specification of how to produce a reproducible training slice or view. Includes collection references, filters, thresholds, sampling strategy, and model targets.

**Training View**
A generated, disposable, reproducible rendering of canonical Atlas data for a specific target model or evaluation scenario. Stored under `training_views/{model}/`.

**Training View Eligibility**
A set of boolean flags per record indicating which model families the record is eligible for. Required keys: `qwen`, `llama`, `deepseek`.

### V

**Validation Agent**
The automation agent that performs comprehensive structural validation by delegating to production validators.

**Verified**
A boolean field on every record indicating human reviewer approval. Required to be `true` before a record can enter the curated dataset.

**Version Index**
A JSON index (`metadata/version_index.json`) mapping dataset versions to their paths, changelogs, and status.

## 15. Vision

### 15.1 The Dataset Factory

Atlas after v2.0 is a **fully automated dataset factory** that transforms raw source data into production-grade training datasets with a single command. The factory is:

- **Deterministic** — every build produces identical output for identical input.
- **Versioned** — every release is a named, checksummed snapshot.
- **Auditable** — every record carries its complete provenance chain.
- **Idempotent** — re-running the pipeline is safe and cheap.

### 15.2 Production-Grade Governance

The governance layer (quality, provenance, revision, validation, approval) becomes a **self-documenting compliance system**:

- Automated policy enforcement via the state machine.
- Human approval integrated at strategic gates (acquisition, release).
- Full audit trail from source selection to published dataset.
- Compliance reports generated automatically per release.

### 15.3 Modular Acquisition

The acquisition subsystem becomes:

- **Plugin-based** — new source types are added by writing a SourceAdapter.
- **Configurable** — each adapter has its own rate limiting, auth, and retry config.
- **Resumable** — interrupted downloads resume from the last byte.
- **Verifiable** — checksums are validated at every step (download → cache → extract).

### 15.4 Multi-Source Ingestion

Atlas ingests from any number of source types:

- **Pre-built datasets** (HuggingFace, Kaggle)
- **Code repositories** (GitHub, GitLab)
- **Documentation** (web docs, wikis, blogs)
- **Q&A platforms** (StackExchange)
- **Academic papers** (arXiv, papers with code)
- **Proprietary/internal data** (private repos, internal wikis)

Each source type uses its own adapter but produces the same Canonical Schema.

### 15.5 Deterministic Releases

Every release is:

- **Rebuildable** — the same source + same pipeline version = same dataset.
- **Verifiable** — file-level checksums in the manifest.
- **Self-describing** — dataset card with stats, license, and provenance.
- **Frozen** — once published, never mutated.

This means a paper that trains on "Atlas v2.3" can be reproduced at any point in the future.

### 15.6 Enterprise-Scale Dataset Pipeline

The pipeline scales to:

- **Thousands of sources** — registry supports categorization, priority levels, and lifecycle states.
- **Millions of records** — streaming processing, parallel workers, efficient caching.
- **Multiple releases** — simultaneous pipeline runs for different versions or branches.
- **Incremental updates** — only re-process sources that changed since the last release.

### 15.7 AI-Assisted Dataset Curation

Post-v2.0, Atlas integrates AI assistance:

- **AI-assisted review** — suggest quality scores and revision proposals (partially done via Quality + Revision Agents).
- **AI-assisted dedup** — use embeddings for near-duplicate detection at scale.
- **AI-assisted transformation** — suggest instruction/QA/reasoning templates from raw content.
- **AI-assisted coverage analysis** — identify gaps in the dataset taxonomy automatically.
- **AI-assisted license analysis** — suggest license classification from README/CONTRIBUTING files.

These are **assistance tools**, not autonomous pipelines — human oversight remains mandatory for all governance decisions.

### 15.8 Atlas Constitution

Atlas is governed by a set of constitutional principles that no implementation may violate:

1. **Atlas is the single source of truth.** Canonical records are the authoritative data representation.
2. **Training views are disposable.** They are generated from canonical data and can be regenerated.
3. **Knowledge objects are immutable after release.** Once included in a release, no record is modified.
4. **Every release must be reproducible.** The same inputs and pipeline version must produce the same output.
5. **Commercial safety is mandatory.** No unlicensed or restricted-license data enters curated releases.
6. **Human review has final authority.** No automated pipeline can release without human sign-off.
7. **Every object must be traceable.** A complete provenance chain exists for every record.
8. **Every score must be explainable.** Quality scores include dimension-level breakdowns and rationales.
9. **No implementation may violate this constitution.**

### 15.9 The Ideal State

In its ideal state, Atlas is a **continuous dataset factory**:

- New sources are discovered and registered.
- A human reviews and approves them.
- The pipeline automatically downloads, caches, extracts, normalizes, cleans, and transforms the data.
- Quality, provenance, revision, and validation agents check every record.
- A human reviews the results and approves the release.
- Training views are generated for target models.
- The release is published with full checksums, provenance, and documentation.
- The entire process is repeatable, auditable, and deterministic.

Atlas is the foundation upon which all future model training is built. The dataset is the durable asset. Models are replaceable.
