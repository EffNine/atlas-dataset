# Release Hardening Design v1

**Phase:** 7C  
**Status:** Design — not implemented  
**Applies to:** `scripts/release/upload_huggingface.py`, `scripts/release/publish_promotion.py`, `scripts/release/build_release_metadata.py`

---

## 1. Problem Statement

The current release pipeline has two classes of defects that make it unsafe for production use without human inspection at every step:

1. **Verification gap:** both scripts check remote file presence and size, but not content integrity. `upload_huggingface.py` collects `lfs.sha256` and silently discards it.
2. **Publish fragility:** `publish_promotion.py` batches all `CommitOperationCopy` ops into one HF commit, which is known to silently drop operations, and has no duplicate-publish guard.

These gaps allow silent corruption or partial publication without detection.

---

## 2. Design Goals

| Goal | Description |
|------|-------------|
| G1 | Remote file content is verifiable byte-for-byte against a local immutable manifest |
| G2 | Resume/skip logic never skips a file whose content differs from local |
| G3 | HF publish uses operation patterns that cannot silently drop |
| G4 | Duplicate publish is detected and prevented before any mutation |
| G5 | Worker configuration comes from unified config, not script-local defaults |
| G6 | Verification failure prevents release_index mutation — no phantom successful publishes |
| G7 | Failure modes are explicit and recoverable without rebuild |

---

## 4. Checksum Manifest

### 4.1 Format

Generated by `build_release_metadata.py` during release build. Stored at `releases/<version>/checksums.sha256`:

```
<64-hex-sha256>  <relative-path-within-release-root>
```

Standard `sha256sum` output format. One line per file. Sorted by path for reproducibility.

### 4.2 Properties

- **Immutable after build.** The file is written once and never modified.
- **Source of truth.** All remote verification reads from this file, never rehashes local files at verify time (which could differ if local files changed post-build).
- **Version-chained.** The checksums file path is recorded in the release manifest so the manifest signature implicitly covers the checksum set.

### 4.3 Loading

```python
def load_checksums(checksums_path: Path) -> dict[str, str]:
    """Return {relative_path: sha256_hex}."""
    out: dict[str, str] = {}
    for line in checksums_path.read_text().splitlines():
        line = line.strip()
        if not line:
            continue
        sha256, _, rel = line.partition("  ")
        out[rel] = sha256.lower()
    return out
```

## 5. SHA256 Verification Module

A shared module `scripts/release/verify_sha256.py` provides the following functions:

### 5.1 `remote_file_meta(api, repo_id, token) -> dict[str, FileMeta]`

```python
@dataclass
class FileMeta:
    path: str
    size: int | None
    sha256: str | None  # lfs.sha256 preferred, fallback regular sha256
    is_lfs: bool
```

Calls `list_repo_files` then `get_paths_info(expand=True)`. Prefers `info.lfs.sha256` for LFS files; falls back to `info.sha256` for non-LFS. Returns `None` for sha256 if neither is available.

### 5.2 `verify_remote(api, repo_id, token, local_checksums, release_root, local_files) -> VerifyResult`

```python
@dataclass
class VerifyResult:
    ok: bool
    problems: list[str]
    verified: int
    failed: int
```

For each local file:

1. Compute `rel = str(local.relative_to(release_root))`.
2. Look up `remote = remote_meta[rel]`. If missing → `MISSING`.
3. Compare `remote.size` vs `local.stat().st_size`. If mismatch → `SIZE mismatch`.
4. Compare `remote.sha256` vs `local_checksums[rel]`. If `remote.sha256 is None` → `NO_HASH`. If mismatch → `SHA256 mismatch`.

**Critical rule:** If a file is LFS but `remote.sha256 is None`, verification fails. This catches files uploaded as regular files instead of LFS.

### 5.3 `should_skip(rel, remote_meta, local_checksums, local_path) -> bool`

Used by both scripts for resume logic. Returns `True` only when:

```python
remote = remote_meta.get(rel)
return (
    remote is not None
    and remote.size == local_path.stat().st_size
    and remote.sha256 is not None
    and remote.sha256 == local_checksums.get(rel)
)
```

## 6. upload_huggingface.py Hardening

### 6.1 Worker Configuration

```python
from parallel.config import resolve_worker_count

# In main():
workers = resolve_worker_count(
    stage="release.upload",
    cfg=cfg,
    explicit=args.workers,  # CLI takes highest precedence
)
```

CLI `--workers` still overrides everything. Without explicit flag, reads from `config.parallelism.yaml → parallelism.release.upload_workers` (default 4).

### 6.2 Retry Model

```python
class RetryPolicy:
    MAX_RETRIES = 3
    BACKOFF_BASE_S = 2.0
    RETRYABLE = (ConnectionError, TimeoutError, ...)  # transient network
    NON_RETRYABLE = (AuthenticationError, ...)         # fail immediately
```

Before each retry, check exception class. Non-retryable exceptions raise immediately.

### 6.3 Resume with SHA256

```python
remote_meta = remote_file_meta(api, args.repo_id, token)
local_checksums = load_checksums(release_root / "checksums.sha256")
pending = _resume_skip(sections, remote_meta, local_checksums, release_root)
```

`_resume_skip` calls `should_skip()` per file. Only fully-matching files are skipped.

### 6.4 Verification Gate

```python
# After all uploads complete, BEFORE index update:
ok, problems = verify_remote(api, args.repo_id, token, local_checksums, release_root, local_files)
if not ok:
    print(f"VERIFICATION FAILED — {len(problems)} problem(s)")
    for p in problems:
        print(f"  {p}")
    return 1  # EXIT WITHOUT updating release_index

# Only now:
update_index(...)
```

### 6.5 Error Reporting

`_verify_remote` returns structured `VerifyResult`. Problems are categorized as `MISSING`, `SIZE mismatch`, `SHA256 mismatch`, `NO_HASH`. Each category maps to a different remediation:

| Category | Remediation |
|----------|-------------|
| MISSING | Re-run upload; resume will pick up missing files |
| SIZE mismatch | Re-upload; likely truncated upload |
| SHA256 mismatch | Re-upload; likely corruption in transit or bad local checksum |
| NO_HASH | Re-upload with LFS enforcement enabled |

## 7. publish_promotion.py Hardening

### 7.1 Single-File Commit Pattern

Replace the single batch commit with one commit per dataset file:

```python
copied = 0
for rf in sorted(src_dataset):
    rel = rf[len("releases/"):]
    dst_rel = "releases/" + args.to_version + rel[len(args.from_version) + 1:]
    
    ops = [CommitOperationCopy(src_path_in_repo=rf, path_in_repo=dst_rel)]
    commit = api.create_commit(
        repo_id=args.repo_id,
        repo_type="dataset",
        operations=ops,
        commit_message=f"Atlas {args.to_version}: copy {rf}",
        token=token,
    )
    copied += 1
    print(f"  copied {rf} → {dst_rel} ({commit.commit_hash[:8]})")
```

One operation per commit. No silent drops possible.

### 7.2 Metadata/Docs Upload

```python
# Single commit for all metadata/docs (small files, not LFS)
ops = []
for section in ("metadata", "docs"):
    ...
commit = api.create_commit(
    repo_id=args.repo_id,
    repo_type="dataset",
    operations=ops,
    commit_message=f"Atlas {args.to_version}: metadata + docs",
    token=token,
)
```

Metadata/docs are not subject to the silent-drop issue because they use `CommitOperationAdd`, not `CommitOperationCopy`.

### 7.3 Duplicate Publish Guard

```python
existing_files = api.list_repo_files(repo_id=args.repo_id, repo_type="dataset", token=token)
prefix_to = f"releases/{args.to_version}/"
existing_at_dest = [f for f in existing_files if f.startswith(prefix_to)]

if existing_at_dest:
    print(f"ERROR: {args.to_version} already published ({len(existing_at_dest)} files on Hub)")
    print("Remove with: hf delete-files ... or run rollback procedure")
    return 2
```

Runs before any mutation. Atomic decision.

### 7.4 Verification

After all commits, verify using the shared `verify_remote` module. Same checksum manifest loaded from local `releases/<to_version>/checksums.sha256`.

```python
local_checksums = load_checksums(to_root / "checksums.sha256")
local_files = [f for f in to_root.rglob("*") if f.is_file()]

ok, problems = verify_remote(api, args.repo_id, token, local_checksums, to_root, local_files)
if not ok:
    for p in problems:
        print(f"  ERROR: {p}", file=sys.stderr)
    print("Publication incomplete — release_index NOT updated", file=sys.stderr)
    return 1
```

### 7.5 Retry for Dropped Copies

If a single-file copy commit returns success but verification shows the file missing or mismatched:

```python
max_copy_retries = 3
for attempt in range(1, max_copy_retries + 1):
    # re-issue single-file copy commit
    ...
    # verify just that file
    ok, problems = verify_single_file(...)
    if ok:
        break
    wait = BACKOFF_BASE_S * (2 ** (attempt - 1))
    print(f"  retry {attempt}/{max_copy_retries}: {rf} — {problems}")
```

## 8. Rollback Strategy

HF Hub has no transactional rollback. The strategy is operational:

### 8.1 Pre-commit Snapshot

Before any publish, record:

```python
pre_commit_files = set(api.list_repo_files(...))
pre_commit_ref = api.get_full_repo_info(...).sha  # last commit hash
```

Stored in a temporary file `releases/<to_version>/.publish_snapshot.json`.

### 8.2 Verification Gate

If post-publish verification fails:

1. Do not update `release_index.json`.
2. Delete the failed publish's files from HF:

```bash
hf delete-files --repo-id EffNine/atlas-dataset --path-in-repo releases/v1.0/...
```

Or programmatically:

```python
for f in new_files_added_this_run:
    api.delete_file(path_in_repo=f, repo_id=..., repo_type="dataset", token=...)
```

3. Remove `.publish_snapshot.json`.
4. Re-run after cleanup.

### 8.3 Idempotent Recovery

After rollback cleanup, the duplicate-publish guard (`P-2`) ensures the script can be re-run safely.

- No changes to release manifest schema or chain_hash format
- No HF upload during design phase
